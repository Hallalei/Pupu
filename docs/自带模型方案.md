# 自带模型方案

让一个 Pupu 改用主人自己的模型，不再用我们的 DeepSeek。很多人手里有自己的 API，或者公司给的模型，想直接用；我们这边也能少花模型费。逐步开放名额以后，这是个要紧的需求。

支持两种接法：

| | 经电脑转发 | 自带 key 存云端 |
|---|---|---|
| 地址和 key 存在哪 | 主人的电脑上（电脑 App 用 safeStorage 加密） | 这个 Pupu 的 SQLite 里 |
| 谁去调模型 | 电脑 | 云端 |
| 电脑关机 | 用不了，可选回落 | 照常能用 |
| 公司内网、VPN 后面的模型 | 能 | 不能 |
| 地址要求 | http 或 https 都行 | 只能 https |

最小实现已经在这个分支上，第 9 节有验证记录。

## 1. 总体做法：路由 provider

会话里记的模型固定是 `pupu/main`（`apps/cloud/src/model/router.ts`）。每次调模型时，路由按当前设置决定真正调谁：

- `pupu`：我们的 DeepSeek，包着每日额度（`withDailyLimit`）。
- `computer`：pi-ai 的 OpenAI 兼容实现，`fetch` 换成桥上的转发。
- `key`：pi-ai 的 OpenAI 兼容实现，key 和地址用云端存的。

之所以固定一个引用，而不是换设置时逐个会话 `setModel`：

- 换设置立刻对所有会话生效，不用迁移。
- pi-durable 每次生成都会调 `getModel()`。路由按当前设置返回上下文长度、能不能看图和单价，所以压缩上下文的时机、截图要不要换成文字说明，都跟着真正在用的模型走。DeepSeek 的上下文是 1M，主人的模型多半只有 32k，沿用 1M 会撑爆。

真正发请求的仍是 pi-ai，它负责拼请求、解析 SSE、拼工具调用、处理重试。我们换掉的只有三样：model 对象、key 和 `fetch`。

不认识的 OpenAI 兼容服务一律按保守的兼容设置（`OWN_COMPAT`）：不发 developer 角色，不带 `store` 和 `strict`，上限字段用 `max_tokens`。原因是 ollama、vLLM 和公司网关常拒这些字段；转发时云端连地址都不知道，也没法靠地址自动探测。

## 2. 经电脑转发的数据流

```
聊天里的一轮
  → pi-durable 调路由 provider（云端 DO）
  → pi-ai 拼好 /chat/completions 请求，调我们给的 fetch（ModelRelay.fetch）
  → 请求体切成 64K 字符一片，经桥的 WebSocket 发给那台电脑：{type:"model", message:{kind:"request", id, seq, text, last}}
  → 电脑收齐，回 ack
  → 电脑用本地的地址和 key 调模型：URL 和 Authorization 一律用本地的，body.model 换成本地的模型名
  → 上游的响应原样传回：head（状态码和 content-type）→ 若干 chunk（SSE 原文）→ end
  → 云端把它拼成一个流式 Response 交给 pi-ai，pi-ai 照常解析
```

代码：

- 帧和云端转发器：`apps/cloud/src/bridge/model-relay.ts`
- 电脑这头：`apps/cloud/bridge/model.ts` 的 `ModelRelayClient`
- 桥上的接线：`hub.ts`（`sendModel`、`modelOf`、`onModel`），`bridge/session.ts` 和 `bridge/run.ts`

**电脑只认请求体。** 云端发过去的只有 body。要调哪个地址、带哪个 key，云端都指定不了。这样即使云端被攻破，也没法借主人的 key 去打内网的其他地址。

**桥连上时，电脑报一次本地模型的信息，设置变了再报：** `{kind:"info", model:{name, vision, contextWindow} | null}`。只有模型名、能不能看图、上下文长度，没有地址和 key。云端把它记在这条连接上，`ComputerView.model` 也带上它，设置页靠它列出能选的电脑。

**超时和取消：**

- 请求体发完 15 秒内没收到 ack，就当电脑没回应。
- 收到 ack 以后，响应头和每一块之间最多等 5 分钟。本地模型处理长上下文可能要好几分钟。
- 用户点停，或者 pi 中止：云端发 `cancel`，电脑停掉上游请求。

**出错时尽量让 pi 能认出来、能重试：**

- 电脑断开或流到一半断了：流报 `relay connection lost`，pi 当作可重试。
- 电脑连不上自己设的模型服务：电脑回 502，正文说「这台电脑连不上它设的模型服务」，带错误码，不带地址，因为这句话会进聊天，成员都看得到。
- 上游的非 2xx 状态码和错误正文原样传回，不改写。pi 靠原文判断上下文超长和要不要重试。

**兼容老的电脑 App。** 协议版本没升，升了会把 0.2.3、0.2.4 全挡在外面。老的桥不认识 `model` 帧，会静默丢掉。老的桥也从不报 `info`，云端就知道它不能转发，直接提示「更新电脑 App」，不会白等。

**地址和 key 存在哪：**

- 电脑 App：用 safeStorage 加密后存在 `userData/model.bin`，密钥在钥匙串里。桥跑的命令读到这个文件也解不开。解开后的内容只经 MessagePort 交给桥的进程，不放环境变量，因为桥跑的命令会继承环境变量。
- 命令行的桥：`~/.pupu/model.json`，权限 0600。key 从环境变量 `PUPU_MODEL_KEY` 读，不走命令行参数，免得留在 shell 历史里。
- 两个文件都加进了文件工具的 `blocked` 名单。

**限制（照实说）：**

- 命令行桥的 `model.json` 是明文。Pupu 在这台电脑上能跑命令，理论上可以 `cat` 它。电脑 App 没有这个问题，因为文件是加密的。
- 电脑 App 里填 key 的表单在设置页上，而设置页是云端发下来的网页。key 只经 preload 交给本机的主进程，不发往云端，但前提是网页代码本身可信。要做到连云端的网页都碰不到 key，得改成 App 自带的本地窗口，像配对窗口那样（见第 10 节）。

## 3. 自带 key 存云端的数据流

主人在设置里填 OpenAI 兼容的地址、模型名、key、上下文长度、能不能看图。云端直接用 pi-ai 的 OpenAI 兼容实现调用，电脑关机也能用。

- 地址只能是 https（本机开发放行 localhost）；内网的模型请改用「经电脑转发」。地址里不能带账号密码。
- key 存在这个 Pupu 的 SQLite 里（`apps/cloud/src/model/store.ts`）。Cloudflare 对 DO 存储做静态加密；我们这边没有再加一层，见第 10 节。
- `state()` 会发给所有成员，所以里面只有来源、主机名、模型名、上下文和能不能看图，没有 key，也没有完整地址。重新保存时 key 留空，表示沿用旧的；换了地址就必须重填。

## 4. 模型能力门槛

| 能力 | 怎么判断 | 不达标时 |
|---|---|---|
| 工具调用 | 保存前探测：带一个 `ping` 工具发一次请求，看回来的是不是 `tool_calls` | 不保存，提示「这个模型没有按要求调用工具……换一个支持工具调用的模型」 |
| 上下文长度 | 主人填，默认 32k | 低于 16k 不让存。Pupu 的系统提示词加工具说明就要占掉不少 |
| 看图 | 主人勾「能看图」 | 不勾时，pi-ai 自动把截图换成「这个模型看不了图」的文字占位。模型知道看不了，不会瞎编 |

探测的代码是 `apps/cloud/src/model/probe.ts`，两种接法共用：

- 经电脑转发：探测在电脑上做，保存时就试，因为只有电脑有 key。
- 自带 key：探测在云端做，换设置时就试。

连不上、key 不对（401/403）、地址不对（404）、格式不对，各有一句对应的提示。

Pupu 做事几乎都靠工具，所以工具调用是硬门槛。Cline 的做法是能力没声明就放行，不支持时悄悄去掉工具（`docs/调研/自带模型先例.md` 第 2 节）。我们反过来：先探测，不过就说清楚为什么。

## 5. 一个团体共用一个 Pupu：用谁的模型，谁付费

- 一个 Pupu 只用一个模型，所有人的主会话、私聊、项目都走它。
- 只有创建者能换模型。用谁的模型、内容发到哪，是整个 Pupu 的事。
- **已定：换模型不要求手机或通行密钥确认**，创建者在任何设备上都能换。换模型虽然等于把所有人的内容（含私聊）改发到别处，但现有的审核点已经够多，不再加一道（2026-11-13 用户确认）。
- 经电脑转发时，可以选任何一位成员的电脑，只要那台电脑上设了模型。那位成员在自己电脑上填 key，就等于同意拿自己的 key 给这个 Pupu 用。费用记在 key 的主人那里，我们不经手。
- 要写进说明：所有成员的内容（包括私聊）都会发到这个模型。所以模型设置所有人都看得到（是哪台电脑、哪个模型、哪个主机），只有 key 看不到。

## 6. 电脑离线时怎么办

- **默认：报错，不回落。** 聊天里显示「「某电脑」现在没连上，用不了它上面的模型。等它回来，或者在设置里换模型。」。不默认回落的原因：主人选自己的模型，常常就是因为内容不该发给别人，比如公司数据。悄悄换成 DeepSeek，等于把它发了出去。
- **可选回落：** 选了电脑之后，设置里出现开关「电脑离线时用 Pupu 自带的」，默认关。打开后，电脑不在线时用我们的 DeepSeek。
- **回落要计入每日额度。** 回落时走的是包着 `withDailyLimit` 的 DeepSeek provider，按 DeepSeek 的单价记账，额度用完就停。
- **只在发起请求前回落。** 判断依据是电脑在不在线。流到一半断了不回落，报 connection lost，交给 pi 重试。
- **其他提示：** 老的电脑 App 提示「更新电脑 App」；电脑在线但没设模型，提示「在那台电脑的 Pupu 设置里填上」。

## 7. 和每日额度的关系

- 用自己模型的请求，model 对象的单价全是 0。pi 算出的 `usage.cost.total` 是 0，`UsageStore` 不涨，也不过额度检查。用自己的模型不扣我们的额度，也不会被我们的额度挡住。
- 只有用我们的模型（选了 Pupu 自带，或者电脑离线时回落）才过额度检查、才记账。
- 目前没给自带模型单独记 token 数。LiteLLM 的经验是 usage 只信 token 数、单价自己算（`docs/调研/自带模型先例.md` 第 3 节）。主人想看用量时再补，见第 10 节。

## 8. 界面

- **设置 →「模型」**：三类选项，「Pupu 自带」「某台电脑 · 模型名」「自己的 key」。大家都看得到，只有创建者能点。选「自己的 key」展开表单，按钮是「试一下并保存」。
- **电脑 App 设置 →「这台电脑」→「这台电脑上的模型」**：地址、模型名、key、上下文长度、能不能看图，加「试一下并保存」和「清除」。老的电脑 App 没有这个接口，页面会先检查，没有就不显示。
- **命令行的桥：**

```bash
PUPU_MODEL_KEY=... node bridge/main.ts model --base-url http://localhost:11434/v1 --model qwen3 --context 32000
```

```bash
node bridge/main.ts model --clear
```

- iOS 还没做模型设置。它收到的 state 里多了 `model` 字段，Codable 会忽略，不影响现有功能。

## 9. 验证

单元测试在 `apps/cloud/bridge/own-model.test.ts`，19 条，覆盖：

- **转发：** 请求体分片收齐；电脑只认请求体（地址、key、模型名换成本地的）；经 pi-ai 跑一轮，工具调用分几块流回来，能拼成完整的调用且不计费；上游连不上回 502 且不带地址；没设模型回 503；电脑不在线立刻失败；取消一路传到上游；流到一半断开报 connection lost。
- **路由：** 离线报错、开了回落才回落、老 App 和没设模型的提示、元数据跟着设置走、用自己的模型不查额度、回落要查额度。
- **中途换模型：** DeepSeek 带思考的历史发给自己的模型，思考去掉、工具调用和结果对得上；自己模型的历史回落给 DeepSeek，照它的要求带上 `reasoning_content`。
- **设置：** https 限制、上下文下限、成员看到的视图里没有 key、key 留空沿用旧的、存取。

端到端（本机验证实例 5199，没有 DeepSeek key，证据在 `.verify-evidence/20261113-own-model/`）：

1. 起一个本地的 OpenAI 兼容假服务。第一轮流式吐 `list_directory` 工具调用，参数分两块发；看到工具结果后，回一句带结果的话。
2. 命令行桥在临时 HOME 里配对。`bridge/main.ts model` 存模型，存之前探测通过，`model.json` 权限 0600。云端的 `computers[].model` 只看到 `{name, vision, contextWindow}`。
3. 网页设置里选「测试电脑 · fake-tools」，见截图 1。
4. 发「看看我主目录里有什么」。模型经电脑转发，调了 `list_directory`，桥执行后，第二次转发的请求带着匹配的 `tool_call_id` 和目录内容，回复是「主人电脑上的模型看到了：hello-from-pupu.txt」，见截图 2。假服务的请求日志显示：带了 21 个工具，没有 developer 角色和 `store`。
5. 停掉桥再发消息，聊天里出现离线提示，没有回落，见截图 3。
6. 换成自带 key（指向同一个假服务）：上下文填 8000 被拒；填 64000 后探测通过、保存成功。再发一轮，工具调用和工具结果都走通，假服务收到了 Authorization，见截图 4。截图 4 里第一张工具卡变成「失败」，是因为假服务每次都用同一个 tool call id，界面把两张卡合成了一张，不是代码的问题。

7. 电脑 App（`open -g`、`PUPU_BACKGROUND=1`、CDP）：在「这台电脑上的模型」表单里填地址、模型名和 key，「试一下并保存」，见截图 5、6。探测带着本地 key 打到假服务；`model.bin` 权限 0600，里面找不到 key 和地址的明文；云端的 `computers[].model` 出现 `fake-tools`。选这台电脑后聊一轮，工具调用走通，上游收到的是本地 key，见截图 7。退出 App 再打开，模型还在。

没验证：

- 真实的 ollama：本机没装。
- 超过 1 MB 的请求体经真实 WebSocket 发送：单元测试测了切片，端到端没有发过大请求体。

## 10. 后续

1. **电脑 App 里填 key 改用本地窗口。** 现在是在设置页里填，要做到网页碰不到 key，可以照配对窗口做一个本地窗口。
2. **云端存的 key 再加一层加密。** 用 Worker secret 派生的 AES-GCM 子密钥加密（LiteLLM 的做法），界面显示 key 的末四位。
3. **自带模型也记 token 数，给主人看用量。**
4. **iOS 设置里加「模型」一节**，只读也行。
5. **补一条端到端：** 装了 ollama 的电脑上用真模型跑一轮。
6. **一台电脑设多个模型**（比如便宜的做压缩、好的做主对话）。现在一台电脑只报一个。

## 先例

克隆在本机的 `references/` 下（只读，不进仓库），对照笔记是 `docs/调研/自带模型先例.md`：

- **Open WebUI 的 Direct Connections。** 服务器把补全请求交给浏览器去调，再逐片传回，和我们的「经电脑转发」同构。我们借了它的骨架：每次请求一个 id、先 ack、逐片回传、最后 done，并补上它缺的分片序号、取消和超时。它的 key 其实存在服务器上，这一点我们没学。它是自定义许可证，只借设计，没搬代码。
- **Cline 的 OpenAI Compatible provider 和模型能力字段。** 借了能力字段的思路，但门槛反过来定：工具调用先探测，不支持就拒绝，不悄悄去掉工具。
- **LiteLLM 的预算和花费记账。** 借了「只用自己的单价算钱，不信上游报的 cost」和「自带模型不扣平台额度」。key 加密入库、`api_base` 加白名单这两点留作后续。
