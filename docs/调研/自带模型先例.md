# 自带模型（BYOM）先例对照笔记

写于 2026-11-12。目的：Pupu 让主人用自己的 OpenAI 兼容模型，有两种接法：
(1) 经电脑转发：key 和地址只在主人电脑上，云端 DO 通过 WebSocket 桥把 HTTP 请求交给电脑，电脑调模型，再把 SSE 流传回来；
(2) 自带 key 存云端，云端直接调。

三个仓库都是 `--depth 1 --filter=blob:none --sparse` 浅克隆，只读，没装依赖，也没跑任何东西。
克隆放在本机的 `references/`，不进仓库。

## 1. Open WebUI：Direct Connections（服务器把补全请求交给浏览器去做）

### 流程（和我们的「经电脑转发」基本同构）

1. **配置和模型列表**：用户在 `src/lib/components/chat/Settings/Connections.svelte:52-54` 填 URL 和 key，然后 `saveSettings({directConnections})`。模型列表由浏览器自己拉：`src/lib/apis/index.ts:122` 调 `getOpenAIModelsDirect(url, key)`，每个模型带上 `urlIdx`。
2. **发起**：前端把带 `direct: true` 的 model 对象随请求发到 `/api/chat/completions`（`backend/open_webui/main.py:1155`、`1194-1196`，以及 `_set_direct_model` 在 `1092-1100`）。服务器照样跑完自己的管线（system prompt、知识库、filter），只把最后一次推理交出去。
3. **服务器转交**：`backend/open_webui/utils/chat.py:109-205`，`generate_direct_chat_completion`：
   - 生成 `channel = user_id:session_id:request_id`（`:130`），并建一个 `asyncio.Queue` 放进 `EVENT_QUEUES[channel]`（`:133-134`，定义在 `socket/main.py:227`）；
   - 用 `event_caller` 发 `{type:'request:chat:completion', data:{form_data, model, channel}}`（`:137-148`）。这是 socket.io 的 `sio.call`，带 ack（`socket/main.py:1877`）；
   - 浏览器 ack 回 `{status:true}` 以后，`event_generator` 从队列里取数据，拼成 `data: ...\n\n` 的 SSE 交给 `StreamingResponse`；收到 `{done:true}` 时结束（`:160-185`）。
4. **浏览器执行**：`src/routes/+layout.svelte:708-795`。按 `urlIdx` 取出 URL、key 和 prefix，`fetch` 上游的 `/chat/completions`（`src/lib/apis/openai/index.ts:398-426`），先 `cb({status:true})`，再把 SSE 逐行 `$socket.emit(channel, line)`（`:762-764`），最后在 `finally` 里 `emit(channel, {done:true})`（`:789-791`）。
5. **回流路由**：`socket/main.py:1482-1503`，通配 `@sio.on('*')`。事件名必须是 `a:b:c` 三段，而且第一段要等于这个 socket 的 user id，才放进本地队列；队列在别的 worker 上时，走 Redis pub/sub 转过去（`:1450-1467`）。
6. **掉线和超时**：`get_event_call`（`socket/main.py:1827-1940`）只允许把请求发给属于同一用户、并且在线的 session（`:1843-1845`），每秒检查一次这个 session 还在不在（`:1889-1893`）；超时默认不限（`env.py:524-532`，`WEBSOCKET_EVENT_CALLER_TIMEOUT`），超时后返回「浏览器标签页可能已关闭」（`:1927`）。没有活跃 WebSocket 时直接报错，后台任务用不了 direct 模型（`chat.py:124-128`）。生成标题、标签这类后台任务改用服务器自己的模型（`chat.py:234-243`）。

### 要注意的事实

- **key 其实也落到了服务器**：`SettingsModal.svelte:475-477` 把整个 `directConnections`（包括 `OPENAI_API_KEYS`）写进 `updateUserSettings`，而后者 POST 到 `/users/user/settings/update`（`src/lib/apis/users/index.ts:306-318`）。也就是说，推理流量不经过服务器，但 key 存在服务器的用户设置里。这和维护者在 #32460 里说的「key 不会到服务器」不一致，以代码为准。我们做「经电脑转发」时，key 必须只留在电脑本地，不能学它这一点。
- 下面几条是我自己读代码看出来的弱点，不是 issue 里报的：
  - `+layout.svelte:762` 用 `chunk.split('\n')` 切分，没有跨 chunk 的缓冲。一行 SSE 被拆在两个 chunk 里时会被切坏，要靠服务器端容错；
  - `chatCompletion` 返回了 `AbortController`，但前端没用它，服务器也没有「取消」消息。用户点停止以后，上游还会继续生成；
  - ack `{status:true}` 之后再出的错，只会变成一个 `done`，服务器分不清是正常结束还是半路断了；
  - `chat.py:163` 的 `queue.get()` 没有超时。浏览器在 ack 之后掉线，服务器这边就一直挂着（只有 `background` 清理）。

### issue

- #32460（已关，读过正文）：很多服务商不开 CORS，direct 模型列表永远是 `[]`；用户想要「服务器代调」，并且关了标签页也能在后台跑。维护者拒绝了，理由是 direct 的意义就是 key 不经过服务器，想让服务器代调就用管理员连接。**对我们**：经电脑转发时由 Electron 主进程发请求，没有 CORS 问题；后台运行要靠电脑在线，所以「电脑不在线」必须有明确的降级或提示。
- #31953（已关，读过正文）：服务器给每个流事件都重新做一次 session 鉴权，这些异步检查让分片互相超车，保存下来的回复乱序或者为空。维护者建议每个分片带单调递增的序号，服务器按序号重组。**对我们**：桥上的每个分片都带 `seq`，DO 端按序号拼接。
- #15162（只在 bot 评论里见过）：多 worker 时 WebSocket 和 API 落在不同实例上，direct 用不了，后来靠 Redis 转发解决。我们是单个 DO，不会有这个问题。
- #24855（未关，只看标题）：direct 连接只支持 Chat Completions，没有 Responses API。
- #31408（未关，只看标题）：反向代理下需要提早发 SSE 头和心跳。

### 对我们的启发

照搬它的骨架：「按请求开通道 + 队列 + 分片回传 + done 收尾」，再补上它缺的四样：分片序号、取消消息、带错误码的结束帧（`{done, error?, usage?}`），以及首包和空闲两个超时。另外，模型列表由电脑去拉，云端只拿到模型 id 和能力。

## 2. Cline：OpenAI Compatible provider 和模型能力

### 配置和能力字段

- `apps/vscode/src/shared/api.ts:72-112`，`ModelInfo`：`contextWindow`、`maxTokens`、`maxInputTokens`（`:77`，和总窗口分开记）、`supportsImages`、`supportsPromptCache`、`supportsReasoning`、价格，以及 `capabilities?: readonly string[]`（`:103-110`）。注释说：这个列表是权威的，不能从布尔字段反推；**没有这个列表就表示「能力未知」，所有检查一律放行（fail open）**。
- `api.ts:119-125`，`OpenAiCompatibleModelInfo` 又加了 `systemRole`（"developer" 或 "system"）、`supportsReasoningEffort`、`supportsTools`、`supportsStreaming`。但在我检出的目录里，`supportsTools` 和 `supportsStreaming` 没有任何非测试代码在读，等于摆设。
- `api.ts:197-205`，`openAiModelInfoSafeDefaults`：用户什么都不填时，默认 128K 上下文、支持图片、价格为 0。
- 能力枚举在 `sdk/packages/shared/src/llms/model-info.ts:22-35`：images、video、tools、streaming、prompt-cache、reasoning、reasoning-effort、computer-use、structured_output、temperature、files。
- `model-info.ts:226-261`：`modelHasCapability` 带 `assumeWhenUnspecified` 参数；`modelSupportsToolCalling` 和 `modelSupportsImageInput` 在能力未知时都放行，理由是「悄悄把图片去掉会丢用户内容」。
- 用户手动填的入口在 `sdk/packages/core/src/services/llms/provider-defaults.ts:300-330`，`buildModelFromPrivateSource`：自定义模型默认带上 `streaming` 和 `tools`，`images`、`prompt-cache`、`reasoning` 按用户勾选加入。
- 设置界面 `apps/vscode/webview-ui/src/components/settings/providers/OpenAICompatible.tsx:561-587`：有「Supports Images」勾选框，可以填 Context Window、Max Output Tokens 和价格。界面上没有「支持工具调用」的开关。key 放在 VS Code SecretStorage（`apps/vscode/src/shared/storage/state-keys.ts:320-329` 的 `SECRETS_KEYS` 里有 `openAiApiKey`）。

### 能力不够时怎么处理

- **工具调用**：`sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts:987-993` 和 `sdk/packages/llms/src/providers/ai-sdk.ts:2373-2378` 判定不支持时，把 `tools` 置空，**不提示用户**。system prompt 按剩下的工具重新生成。
- **图片**：`sdk/packages/core/src/extensions/tools/executors/file-read.ts:254-256`，读图片时如果模型不支持，抛出工具错误 "Current model does not support image input"，让模型自己看到这条错误。
- 设置界面里没有「这个模型不支持 X」的提示（在 `webview-ui/src/components/settings` 里搜 "not support" 没有结果）。**Cline 实际上不怎么提示用户**，这一点值得我们反着做。
- 流式统计：`sdk/packages/llms/src/providers/vendors/openai-compatible.ts:249`，`includeUsage: true`，也就是请求里带 `stream_options.include_usage`。

### issue（都是未关的）

- #14827（只看标题）：在 OpenAI 兼容路线上，`run_commands` 有时收到空的或残缺的参数，循环检测器随后中止了任务。说明流式 tool_call 参数拼接容易出错。
- #12979、#13348（只看标题）：Kimi 和 DeepSeek 的工具调用以 `<|tool_…|>` 或 DSML 标记的形式漏进 content，没有变成 `tool_calls`。
- #15410、#12520、#14550（只看标题）：用户填的 contextWindow 被忽略，压缩时一律按 128K 算。
- #9433（读过正文）：网关返回 `"usage": null`，上下文进度条一直是 0%。
- #15512（只看标题）：本地推理需要可以配置的首包超时和空闲超时。
- #13922（只看标题）：工具描述里写着能读图片，模型不支持视觉时就会报错。

### 对我们的启发

- 能力分三种状态：「已声明支持」「已声明不支持」「未知」。未知时放行，但要**主动探测一次**：用一个带 tools 的极小请求，看返回里有没有 `tool_calls`。
- Pupu 是 agent，**工具调用是门槛**，不能像 Cline 那样悄悄去掉工具。检测不过就不让切换，并且在界面上说清楚原因。
- contextWindow 和 maxTokens 由用户填写或探测得到，必须真正用到上下文压缩里。
- `usage` 可能为空，所以要有本地估算的兜底。

## 3. LiteLLM：预算、花费记账和自定义端点

### 预算检查（请求前）

- `litellm/proxy/auth/auth_checks.py:6742-6818`，`virtual_key_max_budget_check`：`spend >= max_budget` 时抛 `BudgetExceededError`。spend 优先读跨 Pod 的 Redis 计数器（`get_current_spend`），读不到再用缓存。同时异步发出预算告警（`soft_budget` 只提醒，不拦截）。还特别防了 `max_budget=NaN` 的情况（`:6798-6801`），因为 NaN 会让比较永远为假，等于绕过预算。
- 团队、组织、项目、tag 各有一套相同的检查（`:7272` `team_max_budget_check` 等）。
- 预算字段在 `litellm/proxy/_types.py:1803-1840`，`BudgetNewRequest`：`max_budget`、`soft_budget`、`budget_duration`（如 "30d"）、`budget_reset_at`、`tpm_limit`、`model_max_budget`。

### 预留和结算（并发下不超支）

- `litellm/proxy/spend_tracking/budget_reservation.py:250-355`，`reserve_budget_for_request`：调用前用「输入 token 数 + max_tokens 的最坏情况」估出最大成本，先在计数器上**预扣**这笔钱。
- `:357-380`，`reconcile_budget_reservation`：拿到实际成本后多退少补，用 `finalized` 标志保证只结算一次。
- `:403-433`，`release_budget_reservation_on_cancel`：客户端断开或超时的时候，成功和失败两个回调都不会跑。这时**按输入 token 的成本结算**，不全额退回，防止有人在出 token 之前故意中止来逃单。用 `asyncio.shield` 保证这次结算一定能跑完。
- 实际花费写库在 `litellm/proxy/hooks/proxy_track_cost_callback.py:405` 的 `_ProxyDBLogger`，按批写入（`spend_counter_batch.py`）。

### 自定义端点和 BYOK

- `_types.py:1460` 和 `:1568` 的 `is_byok` 属于 `NewMCPServerRequest` 和 `UpdateMCPServerRequest`，是 **MCP 服务器的凭据**，和模型无关。
- 模型层面的「自带」是团队范围的模型行（`model_info.team_id`）：`proxy_server.py:16943-17100` 限定调用者只能看到自己团队的 BYOK 行；凭据加密后入库（`management_endpoints/model_management_endpoints.py:565` 的 `encrypt_value_helper`）。
- 加密实现在 `litellm/proxy/common_utils/encrypt_decrypt_utils.py`：密钥取自 `LITELLM_SALT_KEY`（缺省时退回 master key，`:35-41`），新值用 AES-GCM（`:153-180`），旧值是 nacl SecretBox，靠前缀区分。
- **允许客户端自带 `api_base` 或 key 时的 SSRF 闸门**：`litellm/proxy/auth/auth_utils.py:208-229` 的 `_is_param_allowed`，`api_base` 必须匹配管理员配置的正则白名单；不在白名单里就拒绝，报错见 `:752-768`。
- 模型能力和价格字段在 `litellm/types/router.py:1065-1095`，`ModelGroupInfo`：`supports_function_calling`、`supports_vision`、`supports_reasoning`、`input_cost_per_token`、`output_cost_per_token`、`max_input_tokens`。自定义端点可以自己声明价格。
- 文档目录 `docs/my-website` 已经不在这个仓库里（顶层只剩 `.github`、`litellm`、`tests`），所以没有引用任何文档路径。

### issue

- #14457（已关，读过正文）：大多数服务商只在流的**最后一个分片**里给 usage，客户端提前断开就丢掉了这次的用量。**对我们**：桥断开时按「输入估算 + 已收到的输出估算」记账。
- #35829、#48398（只看标题）：服务商自报的 `usage.cost` 被直接当成美元记账，出现过百万倍的虚高花费。**对我们**：不信任上游报的 cost，只用 token 数乘我们自己的单价算。
- #36926、#43732、#40095、#26672（只看标题）：并发、冷启动、批量写库延迟导致预算误拦或被绕过。
- #40020（只看标题）：进程内的 cost 上限从来不重置。

### 对我们的启发

- DO 是单线程的，对每个 Pupu 来说天然串行，所以「预扣、结算、取消时按输入成本结算」可以直接放在 DO 存储里做，不需要 Redis。
- 「自带 key」对我们来说主要是**不扣平台额度，只记 token 用量**；如果主人自己设了预算，就照 `max_budget`、`soft_budget`、`budget_duration` 这三个概念来做。

## 总结：四个方面各借什么

**经电脑转发**：骨架借 Open WebUI 的 direct 链路（`chat.py:109-205`、`+layout.svelte:708-795`、`socket/main.py:1482-1503`）：DO 为每次请求开 `reqId`，通过桥发 `llm.request`；电脑先 ack，再逐片回传，最后发 `done`。要补上它缺的部分：
- 分片带 `seq`（#31953）；
- 有 `llm.cancel` 消息；
- 结束帧带 `error`、`usage` 和 `finish_reason`；
- 首包超时和空闲超时；
- 电脑一离线就立即失败并提示，不要挂住；
- 电脑端按行缓冲 SSE。

后台任务（标题、摘要）可以按 Open WebUI 的做法退回平台模型，不过要先决定这算不算违背「只用主人模型」。key 只能存在电脑本地（Electron safeStorage），**不要学 Open WebUI 把 key 写进服务端设置**。经由 Electron 主进程发请求，就没有 CORS 问题（#32460）。

**能力门槛**：借 Cline 的三态能力（`model-info.ts:226-261`），但门槛反过来定：工具调用（含流式 tool_calls）是硬门槛。接入时用探测请求验证，不过就拒绝启用并说明原因；图片能力不足时降级，并告诉用户「这个模型看不了图」，不要悄悄丢掉。contextWindow 和 maxTokens 由用户填或探测得到，并真正用在上下文压缩里（Cline #15410）。另外要防住 content 里漏出来的工具标记（#12979）。

**记账和预算**：借 LiteLLM 的「预扣、结算、取消时按输入成本结算」（`budget_reservation.py:250-433`），以及 `max_budget`、`soft_budget`、`budget_duration` 这几个概念。usage 只用 token 数（请求时带 `stream_options.include_usage`），成本用我们自己的单价算，不信任上游报的 cost（#48398）。usage 为空或流中断时用本地估算兜底（#14457，Cline #9433）。自带模型不扣平台额度，但照样记 token，供主人查看。

**key 存储**：经电脑转发时，key 只在电脑的系统钥匙串或 safeStorage 里，云端只知道「这台电脑提供了哪些模型 id 和能力」。key 存云端时借 LiteLLM 的做法：
- 加密后入库（AES-GCM，主密钥放在 Worker secret 里），每个 Pupu 用派生出来的子密钥；
- 界面上只显示 key 的末几位；
- `api_base` 要做 SSRF 防护：拒绝内网、metadata 和私有地址，只允许 https（参考 `auth_utils.py:208-229` 的白名单思路）。
