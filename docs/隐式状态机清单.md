# 隐式状态机清单

2026-11-08 排查。代码取自 `claude/invite-codes` 分支，它包含 main 和线上在跑的功能（邀请码、Cua Driver）。只读了代码，没跑。行号都按这个分支。

「隐式状态机」指一个东西有生命周期，但状态散在几个布尔值、可空字段、时间戳或字符串里，转移分在好几处，没有一个统一的状态类型。

核对一栏的意思：
- **已核对**：我自己对着代码走过这条路径。
- **读码**：排查时读代码得出，我没再单独核对。
- **推断**：代码路径成立，但能不能真碰上取决于时机，没有实际触发过。

分四块（云端、桥、网页和桌面、iOS）排查，一共找到 61 个。下面按影响分成三组；bug 表里每一行是一个具体问题，同一个状态机可能占好几行。最后还列出了已经是显式状态机、不用动的。

## 共性

1. **随时间变的状态没人通知。** 屏幕授权过期、电脑变「不新鲜」、审批过期、登录确认过期，都是读取时现算，没有事件。菜单栏、推送、灵动岛跟不上。
2. **一个东西结束了，它派生出来的东西没跟着结束。** 移除成员不作废他生成的配对码；吊销手机不结束灵动岛；桥断了，远程桌面的输入还开着。
3. **同一个状态多处各算一遍。** 工具步骤的状态，网页和 iOS 都是靠结果文字里的「没有执行：」「作废」来猜的。审批在服务端、网页、iOS、推送、灵动岛各有一份。iOS 的 `Reducer` 是 `transcript.ts` / `view.ts` 的手抄版。
4. **客户端快照没有版本，也不标来源。** 网页的 `api.ts` 和 iOS 的 `Store` 都是后回来的响应覆盖先回来的。iOS 的数据不标是哪个服务器的。
5. **发出去的东西没有「待确认」状态。** 网页和 iOS 发消息、桥上取消命令，都是写出去就当成功了。

## 风险高的（下次改容易出错）

**云端**
- 登录确认（`auth/sign-ins.ts:71-144`）：`used` 同时表示「已签发」和「已作废」，「过期」靠时间现算，过期时不发事件，手机上的「允许 / 拒绝」推送一直留着。
- 成员身份存在两处（`members.ts` 和 `directory.ts`）：移除时先删本地，再 `release`，后一步失败的话，这个邮箱永远被拒。老的根成员没有目录记录，被邀请到别的 Pupu 时会悄悄搬走（`server.ts:1105-1119`、`directory.ts:114-120`）。
- 「还没有创建者」阶段（`members.ts:63`、`server.ts:645-663`）：创建者出现之前生成、出现之后才用掉的配对码或连接器授权，会落成无主的，任何手机都能批准它的写操作。
- 连接器授权（`server.ts:1128-1217`、`connectors/store.ts:154-167`）：先删掉授权记录再去读远端状态，远端还在 `initiated` 或调用抛错时，记录就没了。
- **每日费用上限**（`server.ts:607-611`、`sockets.ts:236-239`）：只在用户发消息时检查。转交给项目（`server.ts:1281`）、建项目后的第一轮、排队的追问、工具循环和重试都不检查。公开试用期间，这条是直接花钱的。
- Pupu 自己的 id 没设置时按根 Pupu 处理，不限额、开连接器（`server.ts:602-620`）。现在的入口都会先设置，新加的入口不一定。
- Durable Object 冷启动：`bridge.onChange` 只在 `onStart` 里接上（`server.ts:403-407`），好几个 RPC 不先调 `lifecycle.start()`，冷启动时 `#admit` 里的通知等于没发。
- 会话订阅（`sockets.ts:168-196`）：`#watch` 在去掉旧订阅和存入新订阅之间有 `await`，两次重叠就会多一份订阅，流式文字出现两遍（推断）。
- 调用者三态（`members.ts:53-65`、`devices.ts:190-196`）：`null` 是本机开发、全放行，`undefined` 是凭据查不到，有些地方把两者当成一回事。
- 灵动岛（`push/live.ts:177-296`）：吊销手机时直接删掉它的令牌，不发 end，灵动岛（可能还带着「允许」按钮）一直留在那台手机上。

**桥**
- 审批（`bridge/approvals.ts`、`gate.ts:194-266`）：中止的一轮记成 `expired`，恢复时提示「10 分钟没人处理」。两个并行的屏幕操作各生成一张请示，批准一张不会处理另一张。吊销电脑之后，它的待批请示还在。`computer_id` 这一列里也存连接器 id。
- 远程桌面租约分在三处（云端 `desktop.ts:261-414`，桥上 `remote.ts:69-202`，电脑端 `apps/desktop/src/capture.ts`、`capture-page.ts`）：拉 TURN 没有超时，卡住时其他手机一直看到「忙」；桥的 socket 断了，`RemoteAgent` 还在跑，点对点输入最多再开 12 秒。
- 桥的连接循环（`bridge/session.ts:43-99`、`run.ts:38-172`）：收到 welcome 就算连上了，其实云端还没接受 `hello`；排队的「收回」在这时发出去，`hello` 被拒的话就丢了；`problem` 只在连上时才清。
- 去重记录（`bridge/actions.ts:18-27`、`147-160`）：桥崩溃或 App 更新之后，记录永远停在 `running`，启动时没有清理。

**网页和桌面**
- 网页快照（`client/api.ts:105-169`）：定时、切回窗口、socket 通知、操作之后都会拉，谁后回来谁赢；`activity` 有两个写入方，没有版本。
- 网页配对码面板（`Settings.tsx:540-612`）：任何新设备出现都算「连上了」，不管是不是用这个码；过期后计时器还在跑；点「不用了」只是藏起来，码在服务端还有效。
- 网页登录（`Login.tsx:65-118`）：`google=false` 同时表示「还不知道」和「没开」；`leaving` 不复位，从 Google 退回来按钮一直转。
- 桌面配对（`apps/desktop/src/main.ts:217-332`、`static/pair.js`）：用码配对和 Google 登录可以同时进行，各生成一台设备，后写的覆盖前面的；配对部分成功后 `reason` 过时，空码重试被挡住；凭据文件的读改写没有串行（`credentials.ts:52-77`）；新账号在系统浏览器里填邀请码超过 5 分钟，回调就打到已经关掉的端口上。
- 桌面的桥子进程（`supervisor.ts`、`bridge-host.ts`）：被拒之后 `#config` 不清，崩溃重启又把吊销的凭据发一遍；退出过程中配对完成，会把桥重新拉起来。
- 电脑端截屏页（`capture-page.ts:122-182`）：连接状态只打日志不上报，对方掉线了还在推流，屏幕也一直不熄。

**iOS**
- `Store`（`Net/Store.swift:8-125`）：数据不标服务器，换连接时还在路上的 A 的响应会写进 B 的界面，还可能用 A 的审批清掉 B 的通知。
- 聊天 socket（`Net/SessionSocket.swift:21-149`）：收到第一条消息才算 `.open`；没有心跳，静默断开后「立即重连」什么都不做；旧的计时器会提前叫醒新一轮退避。
- 远程桌面会话（`Remote/DesktopSession.swift:68-467`）：一个 `State` 枚举旁边还有 `stopped`、`leased` 和 8 个计时器；停止后 `state` 还是 `.live`；`start()` 不重置 `socketFailures`。
- Google 登录页（`UI/ConnectViewController.swift:153-234`）：离开页面后轮询不停，之后要是成功了，会替换掉用配对链接连上的设备；请求进行中还能切换模式，按钮文字和行为对不上。
- 主界面（`UI/ShellViewController.swift`）：`section` 在 `SectionSwitch.selectedIndex` 里还有一份；看过的时间和上次的项目按会话 id 记，不分服务器（见 bug 12）。

## 小而清楚的（不用动）

- 云端：Google 登录流程和邀请码那一步（`auth/routes.ts`、`directory.ts:184-224`），错误次数锁定，设备凭据的 `revoked_at`，会话视图的 reducer，私聊创建，建项目的重放键，APNs 令牌缓存。
- 桥：输入辅助进程（`bridge/input.ts`），菜单栏进程守护，Swift 编译缓存，以及几个小计时器。launchd 不算状态机。
- 网页和桌面：邀请码列表，滚动跟随，长按手势，聊天未读，「这台电脑」开关，新建项目和设置的小开关，主窗口加载和离线页，自动更新，本机回调接收，截屏宿主，退出标记。
- iOS：设置里的配对码和进行中标记，引用回复、滑动回复、跟随底部、标记已读、远程桌面手势。
- 官网（`apps/site/src/scripts/site.ts`）：演示动画的 `visible` / `running` / `played`，内测表单的发送按钮。

## 已经是显式状态机的（排除）

`Thread`（main / private / project）、`ReportState` 和 `statusOf`、`ComputerPolicy` 和 `needFor`、`ActivityState`、`MenubarState.status`、`ApprovalStatus` 的比较后写入、`ConnectionStatus`、网页路由、`PiSessionView` 和 `reduceView`、各种结果类型（`PairResult`、`InviteResult`、`Activation` 等）、桥两端的帧联合类型、`desktopStatus`、iOS 的 `SessionView` 和 `Reducer`、`Push.Status`、`SignIn.Progress`、`ConnectViewController.Mode`。

一轮对话本身（忙、排队、中止）由 pi 管，Pupu 只是转发，没有自己的忙碌标记。项目没有生命周期，只有创建。

## 值得先做成显式状态机的

1. **屏幕授权和桥上的命令调用。** 这里管的是 Pupu 在你电脑上做了什么，碰的是审批这条底线，第 3 到第 7 条 bug 都在这里。屏幕授权改成 无 / 有效（到期时间）/ 已收回 三种状态，所有变化走 `gate.ts` 里的一个函数，到期由定时任务发事件。命令调用的每个终态（正常退出、被用户停掉、已取消、桥断了）都回一帧；取消先记下来，等任务登记上了再处理。
2. **成员移除做成一次级联。** 作废码、断开连接器（失败就不删成员）、释放名额、结束灵动岛，放进一个函数里一起做。顺手把第 2 条（名额）一起修掉，它们动的是同几张表。
3. **工具步骤的状态改由服务端给。** 审批带上 callId，服务端直接发步骤状态，删掉网页和 iOS 里的文字匹配（第 11 条）。

其余的（第 8 到第 10 条、第 12 到第 18 条，还有每日费用上限）都是一两处的修补，不值得为它们引入状态机。
