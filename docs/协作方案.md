# 协作方案

> 日期：2026-11-13。状态：方向已定，第 9 节还有待定项。
> 核心理念：面向整个组织的统一上下文系统。

一个组织共用一个 Pupu。每个人通过自己的个人入口跟 Pupu 说话。要和同事一起做的事，放进空间。组织大脑不是一条聊天，而是藏在背后的那层上下文：空间、资料、进展，按「谁能看」筛过以后，从每个人的入口都连得到。

## 0. 术语

「session」这个词在 pi 里、在我们的代码里、在口头上各指一样东西，所以先把词定死。

| 词 | 指什么 | pi-durable 里是 |
|---|---|---|
| 组织 | 一个 Pupu，一群人共用 | 一个 Session：一个 Durable Object，一份存储，一条提交线 |
| 成员 | 组织里的一个账号，角色是创建者或成员 | 没有，是 `pupu_members` |
| 会话 | 一条对话记录，Pupu 在里面回答 | 一个 Conversation。代码里的 `session` / `PiSessionId` 指的就是它 |
| 个人入口 | 每个成员一条、只有本人和 Pupu 的会话，永远不能分享 | 一个 Conversation |
| 空间 | 一件事的容器：成员、可见档、会话、资料 | 没有，Pupu 自己的表 |
| 密级 | 空间开放到哪一层，参照飞书 L4 机密、L3 秘密、L2 内部、L1 外部可见，见第 9 节 | 没有 |
| 资料 | 放进共享上下文的东西：需求文档、规格、图表 | 没有。不是 pi 的 Document |
| 组织大脑 | 背后的那层：空间、资料、进展的索引，按受众现查 | 没有，是一组工具 |
| 受众 | 能打开一条会话的人 | 由空间成员和可见档算出来 |

界面上：侧栏第一项是「Pupu」，也就是自己的个人入口。下面是空间列表。原来的「大家」变成一个叫「全员」的空间。

## 1. 已定的决定

- **组织大脑藏在背后，不做全员共享的 BigPupu 聊天。** 每个人在自己的会话里问组织的事。（2026-11-13，用户原话：「这个组织大脑可以隐藏在背后，每个人对pupu用各自的私聊conversation」）
- **「个人入口」和「私有空间」是两种东西。** 个人入口每人一条，不能分享，只有它能跨空间读本人有权看的一切。私有空间可以建很多个，能邀请人进来。（2026-11-13，「可以的」）
- **空间默认是私有的。** 只有建的人和 Pupu，可以邀请同事，可以分享。（用户需求原文）
- **Pupu 在每个空间里，一套提示词、一套工具。** 和现在一样，是一个 Registry、同一组 Extension，提示词按会话所在的位置拼。
- **自带模型「经电脑转发」不用特别限制。** 会话全文会经过某个成员的电脑，用户的判断是「没事的，都是自己人」。
- **设计稿这类图片怎么进共享上下文，后面再说。**
- **分享时，以前的聊天给新人看。**（2026-11-13，「给」）
- **一个空间里有一个主会话和若干子会话。主会话只做汇报和委派。**（2026-11-13，用户原话：「主会话只做汇报和委派，就像claude project与cursorproject最近更新的逻辑一样」）怎么约束，见第 5 节「空间里的主会话和子会话」。
- **一个账号有自己的组织，还能加入别人的组织。**（2026-11-13，「一个账号有个人的组织，能加入其他人的组织」）新账号默认在自己的组织里。可以把别人拉进自己的组织，也可以自己进别人的组织。
- **可见档参照飞书文档的 L1 到 L4 密级。**（2026-11-13）具体怎么对应，见第 9 节第 1 条。

## 2. 长期规则

这几条以后加功能时都不能破。权限矩阵测试（第 8 节）就是在检查它们。

1. **一条会话里，只能出现它的全部受众都有权看的东西。** pi 的记录不能改，Pupu 读到的工具结果、渲染进提示词的内容都会留在记录里。所以受众按会话算，不按当前说话的人算。
2. **跨空间读，只在个人入口里做。** 个人入口的受众只有本人，所以能读本人有权看的一切。空间里的会话只读两样：这个空间自己的资料，以及全组织档的东西。这样空间拉新人进来时，记录里不会有他不该看的。
3. **过滤做在工具和接口里，不靠提示词。** 提示词只是第二道。
4. **没有混在一起的「全组织总结」。** 资料和进展按条带着可见范围，有人问的时候按他的受众现查、现拼。后台预先写一份全组织总结，私有内容就混进去了。
5. **从个人入口往空间写东西，算本人发出去的。** 转交说明由 Pupu 起草，挂在本人名下，空间里显示「由谁转交」。本人能撤回。工具层管不住模型写了什么，所以这条要靠两处来守：转交内容在个人入口里给本人看见，空间里写明是谁转交的。

## 3. 和 pi-durable 的对齐

| 规划里的 | pi-durable | 现状 |
|---|---|---|
| 组织 | Session（一个 DO） | 现成 |
| 会话、个人入口 | Conversation | 现成，`harness.sessions.create()` |
| 一套提示词和工具 | Registry + Extension，section 按 `threadOf(session)` 渲染 | 现成，`prompt.ts` 的 `chatPrompt` / `projectPrompt` |
| 派发到空间 | 往另一条 Conversation 提交 Submission | 现成，`hand_off_to_project` |
| 空间里同时做几件事 | 一条 Conversation 同时只跑一个 run，其余排队 | 要多条会话才能并行 |
| 图 3 的 Agents | task 拥有的 Conversation（subagent） | 以后做 |
| 空间、成员、可见档、资料索引 | 没有 | 新建 `pupu_` 表 |
| 资料正文 | 没有。pi 的 Document 是跟会话走的小块 JSON 状态，没有「空间」这一层 | R2 |
| skill、记忆 | 没有 | 以后，见第 9 节 |

分享空间时以前的聊天给不给新人看（第 9 节第 2 条），在 pi 里有两种做法：给看，就是继续用同一条 Conversation；不给看，就是在空间里新开一条 Conversation，带一段交接说明（pi 的 `reset(handoff)` 或新会话的第一条）。

## 4. 数据

都在这个 Pupu 的 DO SQLite 里，和 pi 共用一个库，表名带 `pupu_`。

```
pupu_spaces          id, name, goal, level('L4'|'L3'|'L2'|'L1'), owner_id, created_at, updated_at, progress
pupu_space_members   space_id, member_id, added_by, added_at
pupu_space_sessions  space_id, session, title, created_at          -- 第一版每个空间一条
pupu_entries         member_id, session                            -- 个人入口，每人一条
pupu_docs            id, space_id | null(组织层), title, kind, r2_key, size, author_id, from_session, created_at, updated_at, ended_at
```

- **受众怎么算。** 个人入口的受众是 {本人}。空间会话的受众，在 L4、L3 是空间成员，在 L2、L1 是全体成员（L1 另加只读链接的外部访客）。
- **谁能看哪个空间。** 是成员，或者空间是 L2、L1。
- **会话能读哪些资料。**
  - 个人入口：本人所在的 L3 空间、所有 L2 和 L1 空间的资料，加上组织层的资料。L4 空间不跨读，要进空间看。
  - 空间会话：本空间的资料，加上组织层和全组织档空间的资料。
- **组织层的资料**，`space_id` 为空，全员可见。空间里的资料「提升」到组织层，就是复制一份、记下从哪来。原件留在空间里。
- **资料的可见范围只存一份，用 ACL 字符串表示**：`org`、`space:<id>`、`user:<id>`。检索时先把会话受众能看的 ACL 集合算出来，过滤直接写进查询条件里，不要查完再筛。受众是多个人时，取他们 ACL 的交集。不另设「是否公开」这种标记：改可见范围时，ACL 和检索索引在同一个事务里一起改（Onyx #14981 就是公开标记单独存、没同步，导致改成私有后别人还搜得到）。
- **放宽可见范围只能由主人明确操作。** Pupu 可以把资料引用到范围更窄的地方，不能自己把它转到范围更宽的会话或空间里（Mastodon 的做法）。
- **正文放 R2**，表里只放索引。旧版本标 `ended_at`，不真删（记忆调研里 Graphiti 和 mem0 的做法，见 `docs/调研/记忆.md`）。

现在 `ProjectStore`、`ThreadStore` 直接用 `ctx.storage.sql` 写，没有走 pi 的写入队列。pi 的 README 说过，这样写可能和 pi 的事务一起被回滚。成员和权限搬进这些表之前，要改成和 pi 共用一个 `DurableObjectSqliteDatabase` adapter，或者先证明在 DO 的同步 SQL 下这不会发生。

## 5. 各条路径

- **在个人入口问「组织在做什么」。** Pupu 调 `org_overview`：按本人能看的范围，列出空间、各自的进展一句、最近改过的资料。答案只留在本人的入口里。
- **派活。**
  - 在个人入口说要做一件事：一次性的小事，Pupu 直接做。属于已有空间的，转交过去。要持续推进又没有空间的，Pupu 问一句要不要建，建出来的是私有空间。
  - 转交按第 2 节第 5 条走。
  - 这些和现在聊天里转交项目、建项目的规则一样，只是「项目」换成了「空间」。
- **邀请进空间。** 空间里只能邀请组织里已有的成员。填一个组织外的邮箱，等于先邀请他进组织，再拉进空间，这就碰到第 9 节第 4 条。私有档的空间有了第二个人，就变成成员档。
- **开放给全组织。** 在空间设置里单独打开，变成全组织档。之后所有人能看，组织大脑也会把它答给任何人。
- **移除成员。**
  - 从空间里移除：他再也打不开这个空间。他说过的话留着。
  - 从组织里移除：沿用现在的规则。他的个人入口不再能打开，记录不删（待定，见第 9 节）。
- **电脑和审批。** 规则不变：别人发起的动作按电脑主人设的档来，审批只发到主人那里。改的是「正在做」和审批卡给谁看：原来是「私聊发起的只给发起人和批准人」，以后是「这条会话的受众，加上批准人」。
- **推送和主动消息。** 推给会话的受众。个人入口的推送只给本人。

### 空间里的主会话和子会话

一个空间有一个主会话和若干子会话。主会话只做汇报和委派：接人的需求，拆成子会话去做，收结果，向人汇报。跑命令、改文件、操作浏览器都在子会话里。

开源先例的结论是：要挡住协调者自己动手，靠的是工具层的硬限制，提示词挡不住。Roo-Code 的 Orchestrator 拿不到读写、命令类工具，但还留着一个 `switch_mode`，能切到别的模式自己干。这就是它「协调者绕路自己干」的来源。

Pupu 的做法：

1. **主会话的工具用 `modelTools` 写死。** 只给这几样：
   - 委派：`delegate`、`message_child`、`list_children`、`stop_child`；
   - 读本空间的报告和资料；
   - 只读的组织大脑查询。

   不给 `tool_search`：它会往 `modelTools` 里追加工具，可能把执行类工具加回来。也不给任何「切换模式」类的工具。模型调用了没提供给它的工具，pi 在执行时会拒绝。
2. **委派不阻塞主会话。** 一条会话同时只跑一个 run。如果主会话等子会话做完才算空闲，整个空间就冻住了。所以委派完马上返回，子会话做完后，把结果作为一条新消息投回主会话（opencode 的后台子代理、pi README 例 23 都是这样做的）。重启以后靠请求 id 去重。
3. **子会话是独立配置的。** pi 里子会话会复制父会话的配置，所以要在创建它的同一次提交里重新配：放开执行类工具，去掉委派工具。子会话不能再往下派，只有一层（opencode 默认也只有一层）。
4. **回投只带结果，不带过程。** 只投子会话最后那段话，设长度上限，超出的部分存成资料，只投链接。主会话里留一张卡：任务、状态、摘要，点进去是子会话。四家先例都这样做，长期跑的主会话才不会被撑爆。
5. **人可以直接进子会话说话。**
   - 子会话照常接话。每次 run 结束，都走同一条回投，带上「谁直接说了什么」，让主会话知道（opencode #42670 不让人进子会话，Pupu 要允许）。
   - 主会话再派同一件事时，往已有的子会话里追加，不新开一个。Roo #7131 的坑就是：协调者以为新派的子任务记得上一轮。
6. **同一台电脑、同一个文件同时只给一个子会话写。** opencode #48707 只做了「读完以后内容变了就报错」，没有锁。Pupu 的电脑本来就按台排队，文件写操作按路径串行。
7. **受众不变。** 子会话的受众就是空间的受众，第 2 节的规则照用。

现在每个项目是一条独立的会话，转交是往它 `submit` 一条消息（`server.ts` 的 `hand_off_to_project`），不在同一棵所有权树里。子会话可以保留这种平级的会话，由 Pupu 自己的表记「谁是谁的子会话」，结果回投靠补全 `reports.ts`。这样不用把一个空间收进 pi 的一棵任务树，迁移也简单。这一点在第 1 步实现时定。

## 6. 旧数据迁移

只加表、只加行，不改任何会话 id。迁移要幂等，DO 每次启动都跑一遍也不出错。

| 原来 | 迁成 | 受众 |
|---|---|---|
| 主会话「大家」（root） | 「全员」空间，全组织档，会话还是 root | 全员，和原来一样 |
| 每个项目 | 一个空间，全组织档，会话不变 | 全员，和原来一样（原来项目谁都能看） |
| 每人的私聊 | 他的个人入口，会话不变 | 本人，和原来一样 |

迁完以后，每个人能看到的东西和原来完全一样。

旧版 iOS 和 0.2.x 电脑 App 用的 `/api/state` 里的 `projects`、`chats.main`、`chats.private`，继续照原样给出，等三端都换成新界面后再删。

## 9. 待定和细化

1. **可见档参照飞书的 L1 到 L4（已定方向，对应关系待确认）。** 飞书的文档密级从 L4 到 L1：L4 机密，只给个别相关人员；L3 秘密，给相关成员；L2 内部，可在公司内部分发；L1 外部可见，可以合规地对外分享。

   飞书的密级标签和分享权限是两样东西。下面「密级是可见范围的上限」是 Pupu 自己的设计，不是飞书的规则。

   对应到 Pupu：

   | 密级 | 谁能看 | 组织大脑 | 能不能提升、转出 |
   |---|---|---|---|
   | L4 机密 | 只有空间成员 | 不进。成员的个人入口也不跨空间读它，要看得进空间 | 不能 |
   | L3 秘密（新空间默认） | 只有空间成员 | 成员在自己的个人入口里能读到 | 只能到同为 L3 或 L4、受众不更宽的地方 |
   | L2 内部 | 全组织 | 答给任何成员 | 能 |
   | L1 外部可见 | 组织外也能看（只读链接） | 同 L2 | 能 |

   - 新空间默认 L3，成员只有自己，也就是原来说的「私有空间」。
   - 邀请人不改密级。改成 L2 或 L1 要主人明确操作。降级（比如 L2 改回 L3）也是主人操作。
   - 资料的密级跟着所在空间走，也可以单独调得比空间更严，不能更松。
   - 第一版不做 L1 的对外分享，先做 L4 到 L2。
2. **skill：** 见下文第 9.1 节，建议的做法等你定。
3. **记忆：** 见下文第 9.2 节，建议的最基础版等你定。
4. **被移出别人的组织。** 按已定的「人人有自己的组织，能进别人的组织」：
   - 被移出只影响那一个组织。自己的组织和在别的组织里的身份都不变。
   - 他在那个组织里的个人入口锁起来，谁都打不开，创建者也不行。再被邀请回来时恢复。
   - 他在空间里说过的话、加的资料留着，署名不变。
   - 这一条是默认做法，还没和你确认。

### 9.1 skill 是什么

skill 是一份写好的「这件事怎么做」：一个名字、一句说明、一段做法。比如：
- 「周报怎么写」：从哪些空间取进展、按什么格式、发到哪；
- 「发版流程」；
- 「给客户回邮件的口径」；
- 「报销怎么走」。

在组织里写一次，每个空间里的 Pupu 都按它做。它就是 Cursor 图里底层的 Skills 那一格。

skill 和资料的区别：资料是「是什么」，比如需求、规格；skill 是「怎么做」。

做法照 Anthropic 的 Agent Skills：提示词里只列每个 skill 的名字和一句说明，Pupu 判断用得上时再读正文，所以 skill 多了也不占上下文。

存法就是共享上下文里一种特殊的资料（`kind = skill`），同样带密级，可以属于组织，也可以只属于某个空间。

建议：第 3 步做共享上下文时顺带做最小版，一个列表加一个读正文的工具，成本很小。也可以由 Pupu 起草，人确认后存成 skill，比如「把刚才这个流程存成 skill」。

### 9.2 记忆最基础的版本

最基础的就是「记住一句话」：
- **怎么记：** 人说「记住……」，或者 Pupu 判断这是以后每次都用得上的事（偏好、分工、定下的规矩）。每记一条，对话里都留一行「已记住：……」，人看到不对马上能改。
- **记在哪一层：** 三层，和空间的受众对得上：
  - 个人：关于这个人，只装进他自己的个人入口；
  - 空间：这个空间里定下的事，装进这个空间的会话；
  - 组织：全员都该知道的事，按 L2 处理，装进所有会话。
- **怎么用：** 每条都很短，每层有字数上限，满了让 Pupu 把几条合并。每一轮全量装进上下文，不做检索。装在最新一条消息前面，不放进系统提示，免得每次一变缓存就全失效。
- **怎么改：** 在设置里能看到每一条，能改、能删。改一条，就是旧条标结束、新条接上，记着谁改的。
- **不做：** 后台偷偷从聊天里抽记忆。

以上是 `docs/调研/记忆.md` 的结论，四个开源项目里，hermes-agent 和 OpenClaw 的主路径就是这样。

记忆和资料的区别：记忆短，每轮都装；资料长，用的时候才读。

## 10. 已知上限和风险

- **一个组织一个 DO。** 全组织共用一条提交线，所有会话的写入在一个 DO 里排队，存储受 DO SQLite 的容量上限约束。几十人的团体没问题，更大的组织要拆，到时候再看。
- **`pupu_` 表绕过了 pi 的队列。** 见第 4 节，第 1 步就要处理。
- **转交说明是模型写的。** 第 2 节第 5 条只能做到「写明是谁转交的、本人看得见」，管不住模型往里写了什么。
